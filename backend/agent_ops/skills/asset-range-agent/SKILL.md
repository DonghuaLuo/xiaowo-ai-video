# 规划下一段资产范围

本任务为角色、生物、场景、道具的提取与设计划定原文范围，只有两个创作判断：**下一段资产提取的原文断点**和**是否需要新增整体阶段视觉**。资产断点的目标是保留原文中一次连续的资产出场、介绍或状态变化，使这部分身份与设计依据落在同一范围内。这里的完整指原文已经给出的这一轮资产表达完整，不要求每项资产都有外貌设定，也不要求故事告一段落。阶段视觉概括一个阶段内多数场景共有的可见环境状态；它不是剧情梗概、地点清单、某一场景的画面描述，也不是角色、场景或道具资产。新规划只处理当前游标之后的一段；用户反馈可修订指定的最新未拆分范围，保护已有下游结果。用户反馈修订时保留原任务要求和本次意见；必要时查询同一会话历史。

## 1. 读取本任务专用资料

先区分新规划与修改已有结果。新规划从当前游标开始；用户要求修改已保存范围时，在三项读取和提交中都传 `assetRangeId`，以 `planningState.currentRange` 为原版本，只修改本次要求的内容并保留其余有效约束。仅允许修订最新且尚未开始资产拆分的范围；后端提示已有下游依赖时停止并说明，不能改成规划下一段、删除原范围或拆分资产。没有明确目标时先结合本会话记录确认对象，不借用其他会话的候选。

三项资料返回的 `contextVersion` 必须一致，并原样带入提交；版本变化时重新读取三项，再核对断点与视觉。版本绑定原文、范围状态、参数和阶段视觉，不能用新的版本号替旧资料背书。修订时 `phase_visuals` 返回不含当前范围所建立视觉的基线；当前范围的视觉仍在 `currentRange.phaseVisualContexts`，未要求更改且仍合格时保留。

先调用 `get_asset_range_context(part="source_text")`，只获取当前可选范围的完整原文；不要为重读其中的片段再次调用。接着调用 `get_asset_range_context(part="planning_state")`，取得来源、起点、优先断点、最早允许断点、窗口上限、目标字数和提交版本；这些字段只用于定位与校验，不属于原文。判断新增阶段视觉前，再调用 `get_asset_range_context(part="phase_visuals")`，只获取已有整体视觉并按**视觉含义**比较；旧名称若过于具体，仍以本技能的整体视觉标准判断。

拿到资料后，先在已读原文中比较候选断点及其紧接文字。只有缺少**窗口外**衔接证据时，才用通用 `read_source_window` 从尚未读取的位置接读，范围围绕待补足的那次资产表达；说明缺少什么事实、用新增内容解决什么疑问。补读结果并入本轮已有资料，后续从这些资料直接核对，不再为换一个候选落点重复请求已覆盖的片段。读取偏移沿用工具返回的源文件位置；断点本身通过原文尾句提交，由后端唯一匹配，不需要为计算或复核尾句绝对偏移重读原文。

## 2. 选择并验收资产断点

按以下顺序判断，选点与提交前自检使用同一标准：

1. **定位边界附近的资产表达。** 从 `preferredEnd` 附近向前后核对，找出正在介绍或发生状态变化的角色、生物、场景、道具，以及紧接文字对它们的补充。关注身份辨认、可见形态、场景特征、用途、影响设计的状态和能力表现；行动与对话也可能承载这些事实。只核对与断点有关的对象和事实，无需另做全段资产清单或设计。
2. **保留连续表达。** 若断点把同一资产本次介绍拆成两半，例如前面刚引入对象、后面紧接着补足其身份、形态或状态，就在允许区间内移到这次表达完成之后，或退到这次表达开始之前。某段只有名字或出场动作、原文也未紧接介绍更多信息时，保留原文已有信息即可，不能为了补全未写出的设定而不断延长范围。
3. **区分资产补充与故事继续。** 核对断点后的连续文字是否仍在补足上述资产事实。若只是对话、行动或事件继续，且没有切断资产表达，可以在完整句末分开；剧情悬念、冲突结果和转场只作阅读衔接参考，不能独立证明资产断点合适。若出现新对象，应判断它的新一轮介绍是否完整放在断点的一侧。
4. **在合格落点中择近。** 先满足资产表达完整与允许区间，再优先选择靠近目标字数的自然句末或段末。无需等待整场冲突结束、全段资产全部设计完备或资产后续全部变化；允许区间确无合格落点时，如实说明缺少的衔接证据或范围限制。

`reason` 是给用户看的资产断点依据，用一两句简短中文（建议 40–80 字）交代两件事：**断点附近的具体资产及本次已经交代的身份、形态或状态等事实；紧接的已读文字为何没有继续补足这轮介绍，或新一轮介绍为何完整留在下一段。** 挑选与切点直接相关的一至两项资产事实即可；衔接只说明资产信息是否延续，把事件经过、人物诉求和普通操作过程留在原文里。只写原文能支持的事实，不用全段人物关系或故事梗概代替边界证据。若前后只是日常交流、没有新的资产介绍，可如实说明附近资产信息已交代，当前交流未拆开连续介绍。理由只覆盖已核对的这次连续表达，不声称后续整段都没有资产信息。缺少衔接证据时先按第 1 节补读，再确定断点。有真实未解决风险才写 `riskNotes`。

断点必须落在 `minBoundaryEnd` 至 `planningWindowEnd`。`boundaryEndText` 必须是原文中连续出现、以断点末尾结束的原字原标点，取 20–60 个有效字；末句不足时向前连带原文短句，并在提交前检查有效字数与唯一定位。

## 3. 判断整体阶段视觉

先问：原文在这一范围内是否呈现了**持续、可见、跨多个场景**的整体状态，并且现有阶段视觉无法覆盖？可判断的维度包括时代与世界的可见面貌、资源层级、建筑和环境的维护程度、公共空间秩序、普遍的色彩与材质质感、持续的训练或战斗状态。地点切换、一次事件、人物行动、单个房间或道具，单独都不构成新阶段。世界观变化若只在对话或传闻里出现，也不构成视觉变化。若已有阶段在视觉意义上覆盖本段，`stageVisualChanged=false`，`phaseVisualContexts=[]`；项目没有任何阶段视觉时须建立一个起始阶段。最多追加四项，按原文顺序。

每项新增阶段必须包含以下字段。优先用画面质感、环境维护程度、资源层级、色彩材质、公共空间秩序等**视觉属性**表述；不要把多个地点类型或活动串起来充当一个阶段名称。情绪或生活压力须落实为原文支持的可见环境特征，单独的心理感受不作为视觉属性。训练或战斗可作为变化依据，但结果仍须归纳成可见且持续的视觉状态，而不是“正在做什么”。

- `name`：6–16 字，概括**整体视觉状态**，不写地点、具体事件或道具。
- `visualPrompt`：12–40 字，采用“整体视觉以……为主。”句式，只写大多数场景共有的环境、资源和生活质感。不要写剧情、原因、人物关系、单一建筑、局部场景、后续阶段或否定式要求。
- `sourceSpan`：说明该状态覆盖的原文区间，仅用于追溯来源，不作为视觉提示词。
- `visualChangeReason`：20–80 字，说明相对已有阶段发生了什么**跨场景持续的视觉状态变化**，不要复述故事。
- `transitionType`：起始阶段用 `initial_or_single_stage`；后续新增阶段按真实变化选 `world_state_shift`、`resource_class_shift`、`power_system_shift` 或 `combat_or_training_shift`。

提交前自检：遮住地名、组织名和剧情事件后，`name` 与 `visualPrompt` 是否仍能约束这个阶段的多数场景？它们是否在描述画面中**普遍可见的状态**，而非列举城镇、营地等场景类别或巡守、练兵等活动？若不能，先把跨场景共同的贫富、维护状态、秩序、色彩和材质提炼出来；提炼不出相对现有阶段的新视觉属性，就删掉新增阶段。`visualChangeReason` 须证明持续变化，否则不新增。

## 4. 校验并提交

调用 `submit_asset_range_candidate`，传 `absoluteStart`、`coverageHash`、`contextVersion`、`boundaryEndText`、`reason`、`stageVisualChanged`、`phaseVisualContexts`；修订时必须同时传 `assetRangeId`，按需要传 `sourceId`、`targetUnits`、`riskNotes`。新规划的资产类型沿用后端默认值，修订保留 `currentRange.assetTypes`，除非用户明确要求改变。提交前按第 2 节回查断点两侧：连续资产表达保留在同一侧，理由中的资产事实有原文依据，并且解释的是这个位置为何能分开；再检查游标、尾句、窗口、第 3 节的视觉语义与用户要求。不符合时先调整落点或理由，再提交。后端校验失败时按错误字段修订；来源或版本变化则重新读取专用上下文；不可修复错误停止并说明。

返回 `committed` 表示校验、写入和回读已完成；此时停止，本地程序从已保存断点提取本段结尾和下一段开头，各展示最多 100 字，并展示提交的断点理由。用户反馈修改时结合当前已写入的项目资料和本次意见处理。不要在聊天正文粘贴 Skill、完整原文或工具日志。
